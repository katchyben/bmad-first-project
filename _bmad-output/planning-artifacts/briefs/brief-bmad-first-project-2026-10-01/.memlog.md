- (event) Create intent. Inputs: FastAPI backend, API independent of frontend (frontend open, analyst to recommend), small but complete full-stack project to demo BMad; no code before requirements+architecture; ignore earlier brainstorm sessions
- (decision) Purpose/stakes: personal learning project for Benny to learn BMad (low stakes; right-size brief, no market rigor)
- (decision) Target user of the app: single user managing their own tasks
- (decision) Working mode: coaching path (section by section, with pushback)
- (decision) Core want: a simple list of tasks with due dates
- (decision) Due-date behavior: list sorted by due date; overdue tasks visually highlighted
- (decision) Due date is mandatory on every task (no undated tasks); consequence: adding a task always requires picking a date
- (decision) Due date is a date AND time; overdue = current moment is past the due date-time and task not completed
- (assumption) Time zones: assume single user in one local time zone; store timestamps in UTC, display in user's local time (to confirm in architecture)
- (decision) Task lifecycle: create, edit, mark done; done tasks stay visible in the list
- (decision) Done tasks are immutable: cannot be updated or modified (delete and un-done not yet discussed)
- (decision) Undo allowed for a few seconds after marking done (escape hatch for mis-taps); after the window the task is permanently done
- (assumption) Undo window length assumed 5 seconds (user said 'a few seconds')
- (decision) Delete allowed only for undone tasks; done tasks can never be deleted
- (event) User proposed adding a 'started/in progress' status so accidentally created tasks can be deleted before being started — implied state model under discussion (rules for in-progress delete/edit not yet settled)
- (decision) Adopt task statuses: To do, In progress, Done, Cancelled. In-progress tasks can be edited. Cancelled added to resolve started-but-irrelevant tasks (e.g. cancelled trip)
- (decision) State model confirmed: To do (edit, delete, start, done, cancel); In progress (edit, back to To do, done, cancel; no delete); Done and Cancelled are terminal, immutable, undeletable, each with 5s undo. Delete only from To do (supersedes earlier 'any undone task')
- (decision) Done and Cancelled tasks shown in a separate collapsible section below active tasks; due-date sort applies to active (To do / In progress) tasks
- (assumption) Finished section ordered by most recently finished first
- (decision) Task fields: title, optional description, due date-time (required), status. No priority/tags in MVP
- (assumption) Title required and non-empty (max length TBD in PRD); system fields (id, created/updated, status-changed timestamps) left to architecture
- (decision) MVP includes login/authentication (protects tasks; API must verify caller)
- (decision) Auth: one pre-created account (setup script/config), no self sign-up — app stays genuinely single-user; no password reset
- (assumption) Change-password also out of MVP (credential changed via the same setup mechanism)
- (decision) Primary success criterion: Benny understands each BMad step well enough to use it at work
- (decision) Testable success criterion: Benny can run the whole BMad sequence (brief → PRD → architecture → stories → build) on a new project without help
- (decision) Filtering by status is IN MVP; out of scope: reminders/notifications, recurring tasks, search, subtasks/checklists, mobile app/offline, export/import
- (event) Full brief draft written for user review; dropped Vision section (learning project, not a product roadmap); added Purpose and Problem framing app as vehicle
- (decision) User confirmed all four assumptions (5s undo, recent-first finished section, UTC store/local display, change-password out); converted from [ASSUMPTION] to confirmed decisions
- (event) Polish pass (bmad-review structure+prose) applied to brief and addendum without decision changes; brief finalized
